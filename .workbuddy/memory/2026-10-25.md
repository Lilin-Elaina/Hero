## 17:48 J-Link 上板实锤(板子17:43:49上电, 采样时已运行~4.7min)
- CAN1 与 CAN2 完全相同的死法(寄存器逐位解码, 位号经 stm32h723xx.h 核实):
  - IR(0x50) = 0x09800000 → bit25 BO(bus-off中断标志)置位且一直挂着 → 回调从未处理
  - PSR(0x44) = 0x7E5 → BO(bit7)=1, EW=1, EP=1, LEC=5(Bit0错) → 确诊 bus-off+错误被动
  - CCCR(0x18) = 0x1001 → INIT=1(硬件bus-off后自动置位, 停止一切收发)
  - ECR(0x40) = 0x00F8 → TEC=248(≈31次发送失败×8, 差1步到255满标), REC=0
  - can_rx_total=0(一帧没收到过), RC_Data.last_tick=0(遥控器没开)
- 完整机制(解释所有历史现象): 上电→MCU几ms内起好双CAN→RC_Control_Task每1ms发帧→
  电调(C620/6022)上电比MCU慢/或当时24V没上→无人ACK→每次发送TEC+8→**仅32ms就bus-off**→
  硬件置INIT=1+挂BO中断→bsp.can.c回调 `if(ErrorStatusITs==FDCAN_IT_BUS_OFF) return;` 躺平→
  永久趴窝(哪怕后来电调上电了, 总线也回不来)。
- 为何之前"CAN1能动CAN2不能": 上电竞态——哪路电调恰好在MCU起CAN前ACK就活(CAN1那次活),
  慢32ms以上就死(CAN2那次死)。间歇性、看运气, 与"硬件没问题"并不矛盾(稳态下硬件确实好)。
- 修法(用户改 bsp.can.c:56): `if ((ErrorStatusITs & FDCAN_IT_BUS_OFF) == 0) return;`
  (把"等于bus-off就躺平"反转为"不是bus-off才忽略", bus-off走Stop+Start恢复)。
  修好后若电调未上电, 总线会以~32ms周期自恢复重试(中断风暴风险低, 优先级2), 电调一上电即自动恢复。

## 21:10 通信全通后的混控错乱诊断(纯代码分析, 无J-Link)
用户反馈: LH→自转, LV→前进后退, RV→pitch正常, RH→yaw+前进后退(期望纯横移)。
四因叠加, 全部实证:
1. ★底盘一侧两电机极性反(硬件): fwd指令四轮同值却原地转, 只有"一侧反了"能解释;
   turn/strafe指令反而走直线, 均吻合。恰一侧反(两侧反或零反都会是直线倒退/前进)。
   判定: 推LH看车头往哪甩, 甩向侧=倒转侧 → 该侧两个M_SIGN改-1 (右=ID2/ID3, 左=ID1/ID4)。
2. MECANUM_DIR[0]/[1] strafe符号与文件头注释矩阵相反(LF应+1实-1, RF应-1实+1):
   现strafe列[−,+,+,−]=左右配对=自转模式, 非横移的对角配对[+,−,+,−]。修LF/RF两行。
3. RC_CH_FWD=ch[2]/RC_CH_TURN=ch[3] 与自己注释相反 → 互换(FWD=ch[3]左垂直, TURN=ch[2]左水平)。
4. RC_CH_GIMBAL 与 RC_CH_STRAFE 都=ch[0] → RH同时控yaw+横移。yaw改左拨轮
   `#define RC_CH_GIMBAL RC_Data.wheel`(wheel中值1024, RC_Norm直接可用)。
当前"LH→自转/LV→直线/RH→直线"全为错误①与③(及②)互相抵消的假象, 修复必须四个一起上。
验证顺序: LV上推直线前进(倒退=C翻错边); RH纯横移(带旋转=某侧前后ID对调; 方向反=O型辊整列取反)。
